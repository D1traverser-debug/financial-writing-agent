# Maintenance module

## Ownership
Maintenance owns **how feedback, external methods, code changes and performance evidence become durable system changes**. It does not own article-level prose rules.

## Universal meta-maintenance entry
Financial Writing does not maintain a parallel system-governance doctrine. For any **systemic, architecture-level, cross-surface, non-trivial reliability, or quality-promotion infrastructure change**, first activate the current Universal `operational_hygiene@1.0 + evolution@1.0` semantics through `continuity/UNIVERSAL_PROTOCOL_ADAPTER.json`, then apply this owner-local module for Financial-specific state, writing, quality and deployment details.

A material user correction is a system-impact signal on first occurrence; do not wait for repeated reminders before asking whether the defect generalizes. Classify explicit user content into goal/constraint, failure/counterexample and proposed mechanism. The goal/constraint and real failure evidence are high-value inputs; the proposed mechanism is a candidate, not automatic architecture authority.

For systemic/non-trivial maintenance, the durable maintenance record must cover the current Universal meta-maintenance dimensions that apply, including:
- current authority + full impact/failure model before patching;
- learning/benchmark scout when the change is systemic or architectural, with adoption/rejection rationale rather than copied doctrine;
- at least one credible alternative and an active failure-mode attack on the accepted mechanism;
- an explicit decision on whether repo Skill/startup/account instructions should change or should remain unchanged;
- registry-derived cross-subsystem propagation/inheritance and stale override/shadow-copy review when shared semantics are affected;
- complexity/efficiency cost: authority surfaces, startup context, tool/remote reads, steady-state latency, duplicate rules and migration/test burden;
- regression/eval plus second-order attack on the accepted fix itself;
- a calibrated assurance ceiling and remaining OPEN evidence instead of a global “system has no problems” claim.

A small deterministic owner-local typo/schema/test fixture repair may take a lightweight path when the record gives a concrete `NOT_REQUIRED_WITH_REASON` for the systemic dimensions. Do not turn routine local fixes into bureaucratic full-control-plane research.

The deterministic Universal Meta-Governance Harness verifies process completeness only. It does not make Financial's diagnosis semantically correct, does not prove reviewer independence and does not replace live writing-quality evidence.

## Classify before changing
- Run-local request → current TaskContract/state only.
- Explicit durable user instruction → durable-rule change candidate with direct provenance.
- Single user edit/reaction → raw Writing DNA evidence / one-off candidate, not an automatic global rule.
- Repeated accepted edits across independent articles → eligible for personalized promotion after comparison.
- Post-publication performance → evidence sample; repeated comparable results matter more than one outlier.
- External skill/agent/article/research → benchmark candidate only; distill the underlying mechanism, not signature phrasing or an entire foreign prompt stack.
- Existing rule skipped by execution → runtime/trajectory defect; fix enforcement instead of duplicating the rule in more documents.
- Platform behavior change → reverify current evidence before policy changes.

## Learning evidence
Use `record_writing_learning_sample` (or an equivalent durable receipt) for raw user edits, feedback, acceptance/rejection and post-publication performance when a writing task exists.

For a persisted writing task, a **material explicit user edit, feedback, rejection or acceptance that changes how the system should write, review or deliver** must be captured as owner-controlled learning evidence before the turn claims durable personalized learning or closes the affected revision loop, unless equivalent evidence is already persisted. If evidence capture is unavailable, obey the user's current revision but mark personalized durable-learning persistence as unavailable; do not imply future chats have inherited the lesson.

The ledger is evidence, **not automatic self-modification**. A one-off user reaction never becomes a global style rule by itself.

A repeated material failure of the same writing responsibility is not another reminder-writing opportunity. Treat it as a runtime/trajectory reliability defect: persist failure evidence, identify the enforcement gap, add/update a regression or eval, and remove/repair the conflicting mechanism before adding unrelated writing features.

## Candidate distillation before promotion
A real failure is evidence that something is wrong, not evidence that the first proposed fix is right. Before a quality-changing candidate can enter the blind promotion comparison, `financial_writing_agent.quality_regression.evaluate_candidate_distillation` must PASS.

The distillation package is process evidence, not another article-writing checklist. It must:
- bind the candidate to complete owner-local failure evidence, including at least one real user rejection;
- state the problem and root-cause hypothesis separately from the proposed mechanism;
- compare at least two credible mechanisms and record a failure mode for each;
- record the selected candidate, selection rationale and the smallest intended authority surface;
- include counterexample/failure-mode evidence and a verifiable candidate-change reference;
- independently from simple ref existence, verify that the change/counterexample evidence actually supports this candidate package;
- state the disposition of any superseded mechanism instead of silently accumulating another parallel rule layer;
- scope the quality claim to explicit content modes.

Content-mode scope fails closed. A candidate may claim `FINANCE_DEEP` or `FINANCE_BROAD` quality improvement only when that target mode has complete real-rejection evidence **and held-out coverage spanning at least two distinct topic families**. Evidence from FINANCE_DEEP must not silently authorize a FINANCE_BROAD claim, and vice versa.

This distillation requirement prevents two opposite failure modes: blindly adopting the user's or assistant's first idea, and endlessly adding deterministic prose rules because they are easy to test. It does **not** make the distillation package itself proof of better writing; blind pairwise evidence remains required afterward.

## Quality-changing system promotion
A system/prompt/method change that claims to improve writing quality must not be promoted merely because deterministic CI passes or because the changing agent writes a positive receipt.

Use `financial_writing_agent.quality_regression` for owner-local promotion evidence. Two scopes are intentionally different.

A `COMPLETE` regression/held-out case is not complete merely because a path/ref string exists. It must carry an immutable artifact identity (for example a Git blob SHA, provider immutable version or content digest), and the actual promotion run must verify that binding before the case can be used.

Verifier callbacks are **verification contracts**, not proof of independent execution merely because Python received a callable. When a promotion claim requires independence, the caller must separately establish the verifier/judge execution identity/trace at the execution-control layer.

### General editorial quality
The system may improve general writing quality without waiting for the user to become its optimizer. Promotion requires:
- deterministic factual/compliance/state/artifact invariants remain a hard floor;
- complete real failure evidence with verified immutable case bindings;
- diverse complete held-out evidence spanning **at least two topic families inside every claimed content mode**;
- a passing candidate-distillation package before the candidate is treated as admissible, including semantic verification of candidate-change/counterexample evidence;
- the candidate quality claim is limited to content modes with complete real-failure and held-out diversity coverage;
- a real hard-invariant regression execution receipt bound to the exact candidate/change; an empty caller-supplied regression list is not execution proof;
- blind pairwise comparison against the current baseline with the candidate evaluated in both A and B positions;
- verifiable judge execution evidence;
- every judge run is bound to the exact candidate id and exact candidate-change ref being promoted;
- the judge execution ref verifies and cannot be reused across distinct pairwise runs;
- evidence-ref verification and semantic judge-run verification are separate checks: real refs alone do not prove that the run, candidate binding, blind setup or preference conclusion is valid;
- known real failures improve, held-out cases do not regress, and at least one held-out case prefers the candidate;
- position-swapped judgments must agree or the comparison fails closed.

A user positive label is **not** required for this general scope. External benchmarks and held-out scenarios may support general editorial quality, provided they do not masquerade as personalized taste.

### Personalized Writing DNA
A change that claims to encode the user's personal style or durable preference must satisfy all general-quality requirements **and** include real user acceptance/edit evidence or post-publication performance evidence. External benchmarks cannot invent personalized taste.

Partial snippets/feedback may enter the corpus immediately but cannot by themselves authorize promotion.

`evals/quality_regression.json` is owner-local eval evidence, not business task authority and not a new root policy. The real 2026-10-10 offshore-wind rejection and 2026-10-06 rutile held-out baseline are snapshotted under `evals/artifacts/` with immutable repository identities. They remain evidence, not user-positive style exemplars.

The current corpus is **not quality-promotion-ready** even for FINANCE_DEEP: it has one complete FINANCE_DEEP real rejection and only one complete FINANCE_DEEP held-out topic family. That is enough for diagnosis and candidate design, but not production quality promotion. A second complete FINANCE_DEEP held-out case from a distinct topic family is required before a FINANCE_DEEP candidate may enter the promotion gate. FINANCE_BROAD is also not ready. Personalized Writing DNA remains `NOT_READY` until all general requirements pass and real user acceptance/edit or post-publication performance evidence exists.

## Change protocol
1. For systemic/non-trivial changes, complete the Universal meta-maintenance entry above before treating the first owner-local patch as accepted architecture.
2. Identify the canonical rule owner and affected runtime stages.
3. Decide whether the defect belongs in rules, schema, runtime/state machine, deterministic delivery, tests/evals or deployment—not every problem is a prompt problem.
4. Modify the canonical owner first.
5. Search for contradictory, duplicated or legacy wording/code.
6. Synchronize intentional rule mirrors byte-for-byte.
7. Align schema/runtime/MCP contracts when behavior changes.
8. Add regression tests for both success and failure paths, including revision invalidation/recovery when relevant.
9. Run SDK/MCP smoke, unit/trajectory tests, executable contract evals, static ownership/bundle/version audit, isolated wheel install and DOCX render smoke.
10. When behavior depends on live model/tool execution, run a representative real writing E2E before calling that deployment production-ready.
11. Re-read final authority files and CI state before reporting the change as committed.

## Version / cutover discipline
A breaking schema or public MCP change requires a contract version bump. `pyproject.toml`, `plugin.json`, policy contract version, README/architecture/Site spec and active Continuity metadata must not silently disagree about the current contract.

Do not preserve obsolete compatibility surfaces merely because they once existed. Keep Git history; delete unsupported runtime/schema/tool paths and protect the deletion with static regression checks.

## Runtime reliability discipline
Fail-closed must still be recoverable. A BLOCKED task needs an explicit persisted recovery cursor and a tested resume path; permanent deadlocks are not acceptable durability.

Semantic audit PASS is not a free status bit. A PASS that authorizes a forward transition must be bound to current owner-runtime execution evidence and the persisted audit payload; CHAT_BRIDGED/self-authored provenance without the owner-runtime stage trajectory cannot certify completion. The historical schema label `INDEPENDENT_EXECUTOR` means only a stage-separated owner runtime run in this v0.7 contract; it is **not** provider-attested isolation.

Revisions must invalidate stale downstream QA and stale generated artifacts. Re-running deterministic render/delivery steps must be idempotent so old output cannot contaminate current evidence.

## Evidence standard
A documentation edit is not proof that an Agent executes the behavior. Runtime traces, structured state, artifacts, tests and audit evidence are proof. A real proof object still must be bound to the exact current case/candidate/action; ref existence alone is not semantic proof.
